# การแบ่งงานในกลุ่ม (6-8 คน)

ใช้แบ่งตามความสนใจ แต่มีกฎข้อเดียว: **ทุกคนต้องเข้า server ได้ด้วย key ของตัวเอง**
(ใส่ public key ทุกคนใน `SSH_PUBLIC_KEYS` ของ `config.env`)
→ ตรวจย้อนหลังได้ว่าใครทำอะไรผ่าน `/var/log/auth.log`

---

## ทีมย่อย

### ทีม A — Infrastructure (1-2 คน)
สมัคร VPS, ติดตั้ง OS, จัดการ DNS
- สมัคร VPS (แนะนำภูมิภาค **สิงคโปร์** — ใกล้ไทยสุด latency ต่ำ)
- รัน `00-create-admin-user.sh`, `04-duckdns.sh`, `02-install-lemp.sh`
- เป็นคนเดียวที่ถือ console access ของผู้ให้บริการ (ใช้กู้คืนกรณีล็อกตัวเองออก)
- **ส่งมอบ:** public IP, ชื่อโดเมน, ตาราง spec ของ VPS

### ทีม B — Security / SSH + Firewall (2 คน) ← งานหนักสุด
- รัน `01-harden-ssh.sh` และเก็บหลักฐาน 4 ข้อใน `docs/02-checkpoint-ssh.md`
- รัน `06-firewall-th-only.sh` + ทดสอบ geo-block จากต่างประเทศ (ต้องมี VPN)
- **ส่งมอบ:** screenshot ทดสอบครบ, output ของ `sshd -T`, ผลจาก check-host.net

### ทีม C — WordPress / Content (2-3 คน)
- รัน `03-install-wordpress.sh`, `05-https-certbot.sh`
- ติดตั้ง theme/plugin, ทำเนื้อหาทุกหน้าตาม `docs/04-wordpress-content.md`
- **ส่งมอบ:** เว็บที่เนื้อหาครบ ไม่มี placeholder, ผล PageSpeed

### ทีม D — เอกสาร / นำเสนอ (1-2 คน)
- รัน `99-collect-evidence.sh` แล้วเรียบเรียงเป็นรายงาน
- วาดแผนภาพสถาปัตยกรรมให้สวย (แนะนำ draw.io / Excalidraw)
- ทำสไลด์นำเสนอ
- **ส่งมอบ:** รายงาน PDF + สไลด์ + ตาราง version

## ไทม์ไลน์ (ส่งสัปดาห์สุดท้ายของเดือนตุลาคม 2026)

| สัปดาห์ | เป้าหมาย | ต้องเสร็จ |
|---|---|---|
| **สัปดาห์ที่ 1** (1-7 ต.ค.) | ตั้งต้น | ทุกคนสร้าง SSH key แล้ว, VPS พร้อม, SSH hardening เสร็จ, DNS ชี้ถูก |
| **สัปดาห์ที่ 2** (8-14 ต.ค.) | ระบบใช้งานได้ | LEMP + WordPress + HTTPS ทำงาน, เริ่มใส่เนื้อหา |
| **สัปดาห์ที่ 3** (15-21 ต.ค.) | ความปลอดภัย + เนื้อหา | firewall เสร็จ + ทดสอบจากต่างประเทศผ่าน, เนื้อหาเว็บครบ |
| **สัปดาห์ที่ 4** (22-28 ต.ค.) | เก็บงาน | เขียนรายงาน, ซ้อมนำเสนอ, เผื่อเวลาแก้ปัญหา |

> **เผื่อเวลาไว้ให้มาก** — จุดที่มักเสียเวลาเกินคาด: DNS propagate,
> certbot rate limit (ขอใบรับรองซ้ำได้จำกัด **5 ครั้ง/สัปดาห์ ต่อโดเมน**),
> และการล็อกตัวเองออกจาก server

## กฎการทำงานร่วมกัน

### 1. ห้าม commit ความลับขึ้น git
ไฟล์ที่ **ห้าม** ขึ้น repo:
```
config.env            ← มีรหัส database และ DuckDNS token
*.pem  *.key
id_ed25519 (private key)
report.md (ถ้ามี IP จริง/ข้อมูลผู้ใช้)
```
ใช้ `config.env.example` เป็นแม่แบบ แล้วแชร์ค่าจริงผ่านช่องทางส่วนตัว

### 2. ประกาศก่อนแตะ server
ตั้งกลุ่ม Line/Discord แล้วพิมพ์ก่อนลงมือ เช่น *"กำลังแก้ nginx config นะ"*
สองคนแก้ไฟล์เดียวกันพร้อมกัน = งานหายและ debug ยาก

### 3. สำรองก่อนแก้ทุกครั้ง
```bash
sudo cp /etc/nginx/sites-available/wordpress{,.bak-$(date +%F)}
```
(สคริปต์ในโปรเจคนี้ทำให้อัตโนมัติอยู่แล้วผ่านฟังก์ชัน `backup_file`)

### 4. snapshot ก่อนทำอะไรเสี่ยง
ผู้ให้บริการ VPS ส่วนใหญ่มีฟังก์ชัน snapshot (คิดเงินเล็กน้อย)
**ทำ snapshot ก่อนรัน `06-firewall-th-only.sh`** — คุ้มค่ามาก

### 5. เก็บหลักฐานทันทีที่ทำสำเร็จ
screenshot ตอนนั้นเลย อย่าคิดว่า "เดี๋ยวย้อนมาเก็บ"
เพราะบางสถานะ (เช่น error ตอน login ด้วยรหัสผ่าน) สร้างซ้ำยากเมื่อตั้งค่าไปแล้ว
